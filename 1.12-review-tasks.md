# Chisel 1.12 Release Review Tasks

This checklist tracks the findings from the `v1.11.8` to
`v1.12.0-rc2` release review. Tasks are implemented and reviewed one at a
time; each completed task is committed before work starts on the next one.

## Task 1: Wait for graceful HTTP shutdown to finish

- [x] Complete
- Severity: high
- Problem: `HTTPServer.Wait` waits for `http.Server.Serve`, which returns as
  soon as `Shutdown` closes the listener. The CLI can therefore exit while
  the shutdown goroutine is still draining active handlers.
- Plan:
  1. Make the shutdown/drain operation part of the lifecycle observed by
     `HTTPServer.Wait`.
  2. Preserve immediate refusal of new connections after cancellation.
  3. Preserve the configurable `CHISEL_SHUTDOWN_GRACE` deadline and force
     close any requests which outlive it.
  4. Extend the HTTP server tests so they call `Wait` immediately after
     cancellation and prove that it does not return before an in-flight
     handler finishes.
  5. Add timeout-path coverage proving `Wait` returns after the configured
     grace period when a handler does not drain.
- Acceptance criteria:
  - A normal in-flight request completes before `Wait` returns.
  - New requests are refused once shutdown begins.
  - A stuck request cannot block shutdown past the configured grace period.
  - Existing unit, race, and end-to-end tests pass.
- Implementation review: approved by an independent Sol reviewer; focused,
  full, race, vet, and diff-check validation passed.
- Commit: `fix: wait for graceful HTTP shutdown`

## Task 2: Let cancellation win over retry exhaustion

- [x] Complete
- Severity: medium
- Problem: after `connectionOnce` returns, `connectionLoop` checks
  `MaxRetryCount` before checking whether its context was cancelled. A
  SIGINT/SIGTERM can consequently return `connection attempts exhausted`
  and exit non-zero.
- Plan:
  1. Detect cancellation immediately after `connectionOnce` returns and
     return the normal cancellation result before logging or applying the
     retry budget.
  2. Preserve non-zero failure when a live context genuinely exhausts the
     configured retry count.
  3. Add regression coverage for an already-cancelled context with
     `MaxRetryCount == 0`.
  4. Add coverage for cancellation after a connection has been established
     if it can be done deterministically without timing-sensitive sleeps.
- Acceptance criteria:
  - Context cancellation and CLI signal shutdown return success for every
    retry-count setting.
  - Genuine retry exhaustion still returns `connection attempts exhausted`.
  - Existing retry timing and attempt-count behavior is unchanged.
- Implementation review: approved by an independent Sol reviewer; focused,
  full, and race validation passed. A test-only ephemeral-port TOCTOU was
  noted as non-blocking.
- Commit: `fix: prefer cancellation over retry exhaustion`

## Task 3: Allow every valid SSH packet through the WebSocket limit

- [x] Complete
- Severity: medium
- Problem: the 64 KiB WebSocket message limit is based on an incorrect
  approximately-35-KiB SSH maximum. The pinned `x/crypto/ssh` permits
  packets up to 256 KiB, so large valid configuration requests can be
  disconnected.
- Plan:
  1. Raise the default WebSocket read limit above the SSH transport maximum,
     including framing/headroom, while retaining a finite pre-auth bound.
  2. Keep `CHISEL_WS_READ_LIMIT=0` as the explicit opt-out and preserve
     custom-limit behavior.
  3. Add tests proving a message above 64 KiB but within the supported SSH
     envelope succeeds, while a message above the new default fails.
  4. Update help/release documentation and comments with the corrected
     default and rationale.
- Acceptance criteria:
  - Previously valid SSH/configuration packets up to the SSH maximum are not
    rejected by the default.
  - Oversized pre-auth WebSocket messages remain bounded and rejected.
  - Documentation and tests agree with the implementation default.
- Implementation review: approved after revision by an independent Sol
  reviewer; protocol-boundary, real SSH configuration, environment-isolation,
  focused, and race tests passed.
- Commit: `fix: accommodate valid SSH websocket messages`

## Task 4: Validate release archives before publication starts

- [x] Complete
- Severity: low
- Problem: the CI job currently runs GoReleaser's publishing operation
  before `gzip -t`/`unzip -t`. A failed post-publication check leaves a
  broken draft and pushed version images, and a red job does not
  mechanically prevent a maintainer from publishing that draft.
- Plan:
  1. Add a non-publishing GoReleaser preflight which produces the release
     archives before any registry login or release upload is performed.
  2. Run integrity checks against every preflight `.gz` and `.zip` and fail
     closed if no matching archives were produced.
  3. Execute the real GoReleaser publication only after the preflight passes.
  4. Keep the pinned GoReleaser version and validate the resulting workflow
     and GoReleaser configuration locally.
  5. Update workflow comments so they describe the actual enforcement
     boundary without claiming that a red job blocks manual publication.
- Acceptance criteria:
  - No GitHub release or registry publication step runs before archive
    integrity succeeds.
  - Missing archives make the preflight fail rather than silently pass.
  - The final publication still produces versioned archives, packages, and
    multi-architecture Docker manifests.
- Implementation review: approved after adding `persist-credentials: false`
  to the release checkout; the reviewer confirmed the archive gate, staged
  extra-file checksums/uploads, package and image pipelines, and fail-closed
  shell behavior under GoReleaser v2.17.0.
- Commit: `ci: validate archives before release publication`

## Task 5: Quote untrusted usernames in failed-login logs

- [x] Complete
- Severity: low
- Problem: failed SSH usernames are unauthenticated input and are logged with
  `%s` at info level. Embedded newlines can forge log entries and interfere
  with fail2ban-style consumers.
- Plan:
  1. Render failed-login usernames in a quoted/escaped representation that
     keeps each attempt on one physical log line.
  2. Preserve the remote address and operator-friendly normal username
     output.
  3. Add a regression test using a username containing newline/control
     characters and assert that it cannot create an extra log line.
  4. Confirm successful authentication and returned authentication errors
     retain their existing semantics.
- Acceptance criteria:
  - Untrusted usernames cannot inject physical log lines.
  - Failed attempts remain visible and useful to log parsers.
  - Authentication behavior is unchanged.
- Implementation review: approved after also quoting the aggregated SSH
  handshake error at its debug-log sink; focused tests confirm that both
  failed-login paths remain single-line while authentication errors and
  remote-address reporting retain their behavior.
- Commit: `fix: quote usernames in failed-login logs`
